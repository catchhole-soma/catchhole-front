### Important — R1 (resolved): Adopt successful restart IDs even if the subsequent read fails

File: `worktrees/frontend/src/app/components/catchhole/SEpisodeUpload.tsx:1214` (initial review revision).

The new restart flow awaits `progressQuery.refresh(newJobs, nextScope)` before setting tracked/current IDs and persisting the URL at lines 1216–1219. A successful create POST followed by an unsuccessful bulk GET enters the creation-error catch while keeping the old INVALIDATED scope. The server has already started the new jobs, but this page cannot track them and may offer another creation attempt. This can occur with a transient 500, network loss, or cancellation between the two requests.

Adopt/persist the successful create response independently of refresh success. Keep the seeded new state, close the creation dialog, and represent the follow-up read problem as a status-refresh failure. Add a regression for successful creation followed by failed bulk refresh, asserting new IDs remain in the URL and a later read recovers without another create POST.

Correction reviewed: `SEpisodeUpload.tsx:1214–1224` now adopts and persists the successful create response before refreshing, with an independent refresh-error catch. The new `e2e/analysis-progress-summary.spec.ts:199` regression checks URL/history persistence, reload, status-error display, manual recovery, and exactly one create POST. Root reports 112/112 affected tests GREEN. Generated `AnalysisJobProgressResponse.analysisRun` now includes `null` at `types.gen.ts:8083`, matching the schema customizer and HTTP contract assertion.

### Important / P2 — R2 (resolved): Preserve retry replacement IDs before the follow-up read

Original reference: `src/app/components/catchhole/SEpisodeUpload.tsx:1156–1167` at frontend `5ad9efe`; GitHub review comment `4366253636`.

After a successful retry returned replacement IDs, the page awaited `progressQuery.refresh` before updating its tracked/current IDs and URL. A stalled GET followed by browser reload therefore restored the old IDs and lost tracking of the already-started replacement. This is distinct from the previously corrected new-run restart path.

The final code at `SEpisodeUpload.tsx:1153–1165` adopts and persists successful replacements before the read. It retains old history and unaffected current IDs, preserves superseded handling, and still reconciles rejected/lost responses before classifying retry failures. The new test holds the follow-up GET, asserts the replacement/current/history URL immediately, reloads, and recovers the replacement without a second retry POST.

### Important / P2 — R3 (resolved): Observe invalidated active jobs until terminal

Original reference: `src/app/hooks/useAnalysisJobProgress.ts:25` at frontend `5ad9efe`; GitHub review comment `4366253641`.

Excluding every INVALIDATED ordered job prevented interval, focus/reconnect, and even manual refresh selection from reading a cached PENDING/RUNNING job again. The page's active-job restart interlock consequently stayed locked after the server terminated the job.

The final eligibility check at `useAnalysisJobProgress.ts:22–27` keeps current, non-superseded PENDING/RUNNING jobs eligible before applying the terminal invalidation filter. RUNNING uses the existing three-second interval; invalidated, blocked PENDING uses thirty seconds. Once a terminal invalidated state is observed, polling and focus/reconnect refetch stop. The new parameterized regressions check both statuses, failure-retained interlock, manual recovery, terminal unlocking, and terminal interval/focus/reconnect stop. The existing ordered test now checks the running-to-terminal transition. The prior broad-stop fixture was corrected to terminal invalidated rows, retaining its terminal-stop assertion rather than preserving the buggy lifecycle assumption.
