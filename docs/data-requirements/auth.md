# 데이터 요구사항 — Auth(인증)

로그인·회원가입의 데스크톱 브랜드 패널과 모바일 폼은 공통 `BrandLogo`에서 왼쪽 유광 아크릴 심볼과 오른쪽 기존 CatchHole 워드마크를 함께 표시합니다. 심볼은 각각 44px/48px이며, 인증 요청·약관 동의·라우트 모달 계약은 변경하지 않습니다. [브랜드 적용 기준](../brand-assets.md)

[← 전체 인덱스](./README.md)

랜딩은 네 장면 제품 소개의 제목·설명부터 원고 보호 안내, 핵심 기능, 주요 서비스, 체험 CTA, 푸터까지 최초 화면 진입 시 한 번 페이드 업한다(72px, 900ms, 180ms 시차). 흐림은 2px에서 350ms 안에 해제한다. 모션 감소 설정과 키보드 포커스에서는 즉시 표시한다. 별도 API·저장소 없이 현재 마운트의 DOM 상태만 사용하며 인증 모달·CTA 이동 계약은 유지한다.

핵심 기능은 짙은 블루 패널, 주요 서비스는 업로드·AI 분석 대형 카드 2개와 설정 조회 카드 3개로 구성한다. 예정 기능 3개는 별도 제목 아래 낮은 강조의 카드와 `업데이트 예정` 배지로 구분한다. 모바일에서는 같은 순서의 한 열을 유지한다.

주요 서비스 다음, 마지막 체험 CTA 앞에 `캐치홀을 만드는 마음` 소개를 둔다. 웹소설을 좋아하는 한 독자가 작가의 설정 관리 수고를 줄이고자 시작했다는 제작자의 설명을 담는다. 설정을 찾고 정리하는 시간을 줄이는 목적을 말하며 완전 자동 검수·오류 방지나 후원·투자·운영 이력을 새로 주장하지 않는다. 문단별로 동일한 스크롤 등장을 적용한다.

### 보호 라우트 세션 확인

상태 화면: [인증 확인 중](../screens/Rxd2k.png) · [인증 서버 오류·재시도](../screens/Yj7td.png) · [모바일 확인 중](../screens/zMv34.png) · [모바일 서버 오류](../screens/A8vua.png)

- access token이 있는 상태로 보호 화면에 진입하면 `GET /api/v1/auth/me`로 현재 세션을 확인한다.
- 설정 대시보드 상단의 `설정집 올리기`는 같은 작품의 기존 설정집 업로드 모달로 연결한다. 보호 라우트 세션 확인과 기존 업로드 API 계약을 재사용하며 체험 작품에서는 비활성화한다. [화면 흐름](../screen-flow.md)
- 세계관 후보 검토(`/setting-review?candidateType=world`)와 세계관 DB(`/dashboard?nav=settingDB&tab=worldsettings`)도 같은 보호 라우트 게이트를 통과한 뒤에만 목록·상세 요청과 비교 상태 polling을 시작한다.
- `/setting-review`의 보호 화면 제목은 두 후보 탭 모두 `설정 후보 검토`로 표시한다.
- 401은 인증 만료로 처리해 토큰을 제거하고 로그인 화면으로 이동한다.
- 5xx나 네트워크 오류는 일시적 장애로 처리해 토큰을 유지하고, 보호 화면의 데이터를 노출하지 않은 채 오류 안내와 재시도를 제공한다.
- 세계관 목록·상세·비교 요청의 5xx나 네트워크 오류도 인증 만료로 간주하거나 목 데이터로 전환하지 않는다.

### 사용자 메뉴·회원 탈퇴 (UserMenu)

**노출 위치**: `/works`를 포함해 `UserMenu`를 사용하는 인증 보호 화면의 상단 사용자 아바타. 별도 계정 관리 라우트는 만들지 않는다.

디자인 기준: `design/catchhole.pen`의 `Active / Account / User Menu / Desktop`, `Active / Account / Withdrawal / Desktop`, `Active / Account / User Menu / Mobile`, `Active / Account / Withdrawal / Mobile` 프레임.

**1. 화면에 표시할 데이터**

- 사용자 메뉴 상단에 현재 사용자의 프로필 이미지 또는 이름 첫 글자, 필명(`displayName`), 이메일을 표시한다.
- 보호 라우트가 이미 조회한 `GET /api/v1/auth/me` TanStack Query 캐시를 공유한다. 정보 재조회 중이거나 실패해도 로그아웃과 회원 탈퇴 진입점은 계속 사용할 수 있다.
- 로그아웃 아래 구분선 뒤에 위험 작업인 `회원 탈퇴`를 배치한다. 계정 관리 페이지, 탈퇴 복구, 삭제 진행 상태 화면은 현재 범위에 포함하지 않는다.
- 회원 탈퇴 모달에는 복구 불가 안내, 현재 비밀번호, 고정 확인 문구 `회원 탈퇴`, 취소와 최종 탈퇴 버튼을 표시한다.

**2. 상호작용·접근성 계약**

- 사용자 메뉴 버튼은 열림 상태를 `aria-expanded`로 알리고, 메뉴를 열면 첫 액션으로 포커스를 이동한다. `ArrowUp`·`ArrowDown`·`Home`·`End`로 액션을 이동하고 `Esc`로 닫아 트리거에 포커스를 돌려준다.
- 회원 탈퇴를 선택하면 사용자 메뉴를 닫고 확인 모달을 연다. 모달은 첫 비밀번호 입력으로 포커스를 이동하고, 포커스를 내부에 가두며, 닫힌 뒤 사용자 메뉴 트리거로 복원한다.
- 현재 비밀번호는 필수·최대 64자다. 확인 문구가 공백을 포함한 `회원 탈퇴`와 정확히 같을 때만 최종 버튼을 활성화한다.
- 요청 중에는 입력·닫기·배경 선택·`Esc`·최종 버튼을 잠가 중복 요청을 막는다.
- 320px 화면과 200% 확대에서도 메뉴와 모달이 가로로 넘치지 않아야 하며, 낮은 화면에서는 모달 본문을 내부 세로 스크롤한다.

**3. API·세션 계약**

```http
DELETE /api/v1/members/me
Content-Type: application/json

{
  "currentPassword": "사용자가 입력한 현재 비밀번호",
  "confirmation": "회원 탈퇴"
}
```

- 생성 SDK의 `withdrawMe`를 MutationCache를 거치지 않고 직접 호출하며 비밀번호와 확인 문구를 로그·브라우저 저장소·Query/Mutation 캐시에 기록하지 않는다.
- `202 Accepted`를 받은 뒤에만 진행 중인 refresh를 무효화하고 access token과 전체 Query/Mutation 캐시를 지운다. 이후 `/landing`으로 현재 히스토리 항목을 대체하고 한 번만 보이는 탈퇴 접수 안내를 전달한다.
- 랜딩은 안내를 화면 로컬 상태로 옮긴 직후 history state의 `memberWithdrawalAccepted`를 제거한다. 새로고침이나 뒤로가기로 같은 성공 안내를 반복하지 않는다.
- 비밀번호 불일치(`MEMBER_WITHDRAWAL_PASSWORD_MISMATCH`)는 현재 비밀번호 필드 오류로 표시한다. 요청 검증 오류는 해당 필드에 표시한다.
- 400·네트워크·일반 서버 오류에서는 모달, 두 입력값, access token과 캐시를 유지한다. 탈퇴 API가 refresh와 원 요청 재시도 뒤에도 401이면 `/auth/me`로 세션을 재검증하고, `/auth/me`도 401일 때만 세션을 제거한다. 세션이 유효하거나 확인할 수 없는 5xx·네트워크 오류에서는 입력과 세션을 유지한다.

**4. BE → FE 제공 데이터 요구사항**

| 데이터 의미 | 현재 필드·상태 | 화면 사용 |
| --- | --- | --- |
| 현재 사용자 요약 | `displayName`, `email`, `profileImageUrl` | 메뉴 프로필 요약과 아바타 fallback |
| 탈퇴 요청 접수 | HTTP `202`, `requestId`, `status` | 성공 여부 판정. 비동기 삭제 상태 화면은 제공하지 않음 |
| 비밀번호 불일치 | `MEMBER_WITHDRAWAL_PASSWORD_MISMATCH` | 현재 비밀번호 필드 오류 |
| 요청 검증 실패 | 오류 `details[].field`, `details[].message` | `currentPassword`·`confirmation` 필드 오류 |

**5. FE → BE 전달 데이터 요구사항**

- `currentPassword`: 사용자가 입력한 원문, 필수, 최대 64자
- `confirmation`: 공백을 포함한 고정 문자열 `회원 탈퇴`

### 상시 서비스 의견 (FeedbackDialog)

**노출 위치**: `UserMenu`를 사용하는 인증 보호 화면의 상단 아바타 왼쪽. 데스크톱과 모바일 모두 `의견 보내기` 아이콘과 라벨이 있는 강조 버튼을 표시한다. 터치 높이는 44px 이상이며 좁은 화면에서는 헤더를 두 줄로 배치할 수 있다.

디자인 기준: `design/catchhole.pen`의 `FeedbackDialog / 상시 서비스 의견` 프레임. 랜딩 전용 `DESIGN.md` 토큰은 적용하지 않고 인증 화면의 Theme V2 `--ch-*` 의미 토큰을 사용한다.

**1. 입력·상태 계약**

- 의견은 앞뒤 공백을 제외한 Unicode 10~1000자로 입력하며, 원고 내용이나 민감정보를 입력하지 않아도 된다고 안내한다.
- 현재 화면은 query와 fragment를 제외한 `window.location.pathname`만 `pagePath`로 전송한다.
- 제출 중에는 입력·중복 제출·배경 선택·`Esc`·닫기를 잠근다. 실패 시 입력을 유지하고 성공 시에만 비운다.
- `CREATED`는 의견과 일반 피드백 보상 요청이 함께 접수됐다고 안내한다. `ALREADY_REQUESTED`는 의견만 새로 저장되고 이전 보상 요청을 재사용한다고 안내한다. `PENDING_REQUEST_EXISTS`는 다른 추가 사용량 요청이 처리 중이라 의견만 저장됐다고 안내한다.
- 성공 안내를 닫으면 상단 `의견 보내기` 트리거로 포커스를 복원한다. 320px와 실제 200% 확대에서도 헤더와 모달이 가로로 넘치지 않아야 한다.

**2. 계정당 한 번의 자동 안내 (#196)**

- 활성 작품에 등록한 보관되지 않은 회차가 계정 전체 합계 3개 이상이고, 기존 일반 의견 및 안내 노출 기록이 없는 계정만 대상이다. 마지막 회차 번호는 개수로 사용하지 않는다.
- `GET /api/v1/feedbacks/prompt`의 `data.shouldShow`는 대상 여부만 조회한다. `POST /api/v1/feedbacks/prompt/claim`이 계정별 잠금으로 노출을 한 번 부여하고 기록하며, 반환된 `shouldShow=true`일 때만 안내한다.
- `/dashboard?nav=manuscripts`에서 실제 회차 목록 조회가 성공하고 분석이 진행 중이지 않을 때 안내한다. 업로드·검토 화면, 열린 모달·사용자 메뉴, 입력 중, 비활성 탭에서는 자동 노출을 보류한다.
- 제목은 `캐치홀을 사용해 주셔서 감사합니다!`, 동작은 `의견 남기기`와 `닫기`다. 의견 남기기는 기존 입력 폼으로 연결한다. 닫기·Esc·배경 닫기 후에는 서버 기록으로 재노출하지 않는다.
- 노출 API 실패나 권한 부여 후 화면 이동 시 자동 안내를 생략하며 수동 의견 보내기는 유지한다. 브라우저 저장소에 계정별 노출 이력을 복제하지 않는다.
- 일반 의견만 10~1000자로 완화하며, 사용량 소진 추가 요청의 35~1000자 계약은 유지한다.

**3. API·보상 계약**

```http
POST /api/v1/feedbacks
Content-Type: application/json

{
  "content": "사용자가 작성한 서비스 의견",
  "pagePath": "/dashboard"
}
```

- Backend는 유효한 의견을 `feedbacks`에 매번 새 행으로 저장한다.
- 첫 일반 피드백은 기존 추가 사용량 승인·지급 흐름의 `GENERAL_FEEDBACK_REWARD` 요청을 함께 만든다. 이 출처의 요청은 `PENDING`, `APPROVED`, `REJECTED` 전체 상태를 통틀어 회원당 한 번만 존재한다.
- 다른 추가 사용량 요청이 `PENDING`이면 의견은 저장하되 이번 보상 요청 생성은 보류한다. 이후 다시 의견을 보낼 때 대기 요청이 끝났고 일반 피드백 보상 이력이 없으면 최초 보상 요청을 생성할 수 있다.
- 보상 승인은 기존 운영자 API와 `AI_TOKEN_DEFAULT_GRANT`를 사용하며, `usedTokens`와 `reservedTokens`를 초기화하지 않는다.

| 데이터 의미 | API 필드·상태 | 화면 사용 |
| --- | --- | --- |
| 의견 본문 | `content`, trim 후 10~1000 Unicode 글자 | 입력 검증과 운영 검토 |
| 작성 화면 | `pagePath`, 내부 pathname | 의견 발생 화면 구분 |
| 보상 요청 결과 | `rewardRequestOutcome` | 생성·기존 요청·다른 대기 요청 구분 |
| 연결 요청 | `rewardRequestId`, `rewardRequestStatus` | 성공 안내 분기. 정확한 token 수치는 노출하지 않음 |

### 인증 사용자 AI 사용량

- 사이드바의 남은 사용량 게이지·퍼센트와 이를 위한 polling은 제거한다. 정확한 token 수치도 표시하지 않는다.
- 사용량 소진 시의 안내와 추가 사용량 요청 흐름은 유지한다.
- 분석 생성·재시도 요청에서 `AI_TOKEN_QUOTA_EXHAUSTED`를 받으면 해당 요청을 시작한 확인 모달을 먼저 닫고 전역 사용량 소진 모달을 연다. 피드백 제출 또는 검토 중 안내 확인 뒤 이전 확인 모달이 다시 드러나지 않아야 한다.
- 분석 시작 뒤 비동기 Job 조회에서 같은 failure code를 확인해도 전역 모달을 연다. 같은 배치의 현재 Job이 모두 terminal 상태가 된 뒤 1차 추출 전 실패는 단일·전체·일부 실패 회차 수에 맞는 문구와 실패 회차 재시도를 안내하고, 1차 추출 뒤 비교 일부 중단이면 중단 건수, 완료 결과 보존, 세계관 검토에서 재개할 수 있다는 안내를 표시한다. 한 배치에 두 종류의 실패가 섞이면 실패 회차 수와 보존된 세계관 비교 중단 수를 한 모달에 함께 표시한다.
- 소진 모달을 열 때 `GET /api/v1/ai-token-usages/extension-requests/me/pending`으로 미처리 요청을 확인한다. 요청이 있으면 새 입력 폼 대신 운영자 검토 중 상태를 표시하고, 한 회원이 동시에 두 요청을 만들지 않게 한다.
- 소진 모달에서 생성한 요청은 `QUOTA_EXHAUSTION`, 상시 서비스 의견에서 회원당 한 번 만드는 보상 요청은 `GENERAL_FEEDBACK_REWARD` 출처로 구분한다. 운영자 승인·반려와 지급 원장은 같은 API와 상태 전이를 재사용한다.
- 새 요청은 단일 입력란의 앞뒤 공백을 제거한 Unicode 글자 수가 35~1000자일 때만 `POST /api/v1/ai-token-usages/extension-requests`로 보낸다. 입력 폼은 `제출`과 `취소` 액션을 구분한다. Front와 OpenAPI DTO가 같은 제약을 적용하며, 원고 본문·민감정보를 자동 첨부하지 않고 입력하지 말라는 안내를 함께 표시한다.
- 요청 body는 `feedback`과 모달 발생 원인인 `context`를 전달한다. 동기 차단은 `REQUEST_BLOCKED`, 1차 분석 실패는 `ANALYSIS_FAILED`, 1차 추출 뒤 비교 중단은 `ANALYSIS_INTERRUPTED`로 구분한다.
- 제출 중에는 중복 전송과 모달 닫기를 막는다. 성공하면 입력을 비우고 검토 중 상태로 전환하며, 실패하면 입력을 보존한 채 다시 시도할 수 있게 한다.
- 운영자 승인·반려 화면은 Front MVP 범위에 포함하지 않는다. 승인은 Backend 운영 API가 처리하며 승인량은 신규 회원의 초기 지급량과 같은 설정값을 사용한다. 누적 지급량·사용량은 초기화하지 않되 사용자용 비율은 현재 1회 제공량을 기준으로 최대 100%까지 표시하며, 정확한 token 수치는 사용자에게 노출하지 않는다.
- 서비스 이메일은 피드백 폼의 대체 수단이 아닌 보조 연락처로 계속 표시한다. Theme V2의 밝은 문의 영역에서 이메일 링크는 4.5:1 이상의 명암비를 갖는 의미 색상과 밑줄을 사용한다.
- 사용량 조회의 401은 기존 보호 라우트 세션 갱신·로그아웃 정책을 그대로 따른다.

| 데이터 의미 | API 필드·상태 | 화면 사용 |
| --- | --- | --- |
| 피드백 본문 | `feedback`, trim 후 35~1000 Unicode 글자 | 글자 수 검증과 운영자 검토 내용 |
| 요청 출처 | `source` | 사용량 소진 요청과 일반 피드백 보상 요청 구분 |
| 요청 발생 원인 | `context` | 동기 차단·분석 실패·비교 중단 구분 |
| 미처리 요청 | `pending`, `request.status=PENDING` | 중복 폼 대신 검토 중 상태 |
| 처리 결과 | `APPROVED` 또는 `REJECTED` | 현재 모달에서는 직접 조회·노출하지 않음 |

**1. 화면에 표시할 데이터**
- 상단 고정 헤더: CatchHole 로고, 서비스 소개·주요 서비스 앵커, 로그인·무료 시작 보조 버튼, `로그인 없이 체험하기` 주 버튼
- Hero: 승인된 실사 영상(작가 → 노트북 원고)을 사용한다. 첫 화면은 흰 여백과 둥근 모서리, 영상 하단의 `설정 추출부터 검수까지 / 캐치홀 하나로` 제목으로 시작한다. 첫 장면에는 큰 제목만 표시하고, 체험 주 버튼·무료 시작 보조 버튼과 원문 근거·작가 확정 안내는 마지막 장면에서 표시한다. 마지막 영상 프레임에서 `잊힌 불씨 / 25화. 북쪽 성문` 원고와 세계관 3개·캐릭터 1개·마법 2개의 설정으로 이어진다. 소개용 설정 확정은 서버에 저장하지 않는다.
- Hero 설정 추출 장면의 보조 문구는 `작성한 원고를 업로드하면`, 제목은 `캐릭터와 세계관 설정을 추출해요.`로 표시해 업로드 조건과 추출 대상을 명확히 안내한다.
- 제품 기능 소개: 기존 8단계 탭·자동 순환을 제거하고 원고에서 발견 → 원문과 함께 확인 → 나만의 설정집 → 변화의 기록, 네 장면을 스크롤로 읽는다. Craft의 부드러운 색 배경과 겹친 문서, Linear의 핵심 화면 확대 방식을 참고했다. 900px 이하에서는 설명 다음에 화면을 쌓는다. 마지막 장면의 링크는 공개 `/demo`로 이동한다.
- 원고 학습 미사용 안내: 제품 데모 아래, 핵심 기능 3항목 요약 위에 항상 펼쳐진 간결한 섹션으로 표시한다. 제목은 `작가님의 원고는 AI 학습에 사용하지 않습니다.`, 본문은 `원고와 분석 결과 모두에 적용됩니다.`로 유지하고 `개인정보 처리방침 보기` 링크를 제공한다. 이 약속의 범위는 원고·분석 결과의 자체·외부 AI 모델 학습 미사용이다. 인접 섹션과 같은 캔버스 배경·콘텐츠 폭·왼쪽 정렬을 유지하고 `AI 학습에 사용하지 않습니다.`를 강조한다. 제목은 데스크톱 최대 32px·모바일 최소 26px, 위아래 여백은 데스크톱 56px·모바일 40px로 유지하며 `/landing#manuscript-protection`으로 직접 연결할 수 있다.

**2. 상호작용·반응형 계약**
- 영상 Hero는 실제 `.landing-page` 스크롤 컨테이너를 기준으로 동작한다. 데스크톱은 스크롤·마우스 드래그에 따라 여백과 모서리가 줄어들고 영상이 진행된다. 역방향 스크롤은 같은 장면을 되돌린다.
- 영상이 끝난 뒤 마지막 프레임의 노트북 화면에서 선명한 원고 화면으로 연결하고, 원고 주변에 설정 6개를 펼친다. 이동 중인 영상에 글자를 추적 합성하지 않는다. 종류별 확정·처음 장면으로 돌아가기를 제공한다. 설정 추출·확정이 끝나면 체험·무료 시작 CTA를 표시한다.
- 680px 이하 모바일에서는 긴 고정 스크롤 구간 없이 음소거 인라인 영상을 일반 재생한다. 영상이 끝나면 같은 위치에서 25화 원고를 보여주고 약 18초 동안 세계관·캐릭터·마법 카드가 순서대로 펼쳐지고 확정된다. 카드 3개 안의 설정 6개는 데스크톱과 같은 데이터이며 작은 화면에서는 읽을 수 있는 세로 배치를 사용한다. 스크롤은 영상 시간이나 추출 진행률을 변경하지 않고, 자동 스크롤도 하지 않는다.
- 모바일 영상·설정 추출은 각각 일시정지·재개할 수 있고, 설정을 직접 확정하면 자동 진행을 멈춘 뒤 해당 확정 상태를 보여준다. 설정 6개의 확정이 끝난 뒤에만 완료 문구·체험·무료 시작 CTA가 나온다. 처음부터 다시 보기는 영상과 모든 설정 상태를 초기화한다. 로그인 모달이나 숨겨진 탭에서는 영상과 추출 진행을 멈춘다. 영상 자동 재생이 차단되면 기본 재생 컨트롤을 표시한다.
- 모션 감소 설정에서는 영상 자동 재생과 스크롤 진행을 중단한다. 데스크톱은 버튼으로 정적 원고·설정 장면을 탐색하고, 모바일은 수동 영상 재생이 끝나면 원고·설정을 정적으로 보여주며 종류별 확정으로 마지막 CTA에 도달한다.
- 네 장면은 현재 `/demo`에서 실행되는 제품 컴포넌트의 가상 데이터 화면을 캡처해 보여준다. 검토는 실제 `CandidateDetail`, 인물·세계관·이력은 실제 `CharacterDatabase`·`WorldSettingDatabase`·`CharacterTimelineModal`이며 옛 미니어처 JSX는 제거했다. 모바일 검토 화면은 별도로 캡처한다. 사용자 원고나 인증 데이터는 사용하지 않는다.
- 캡처는 랜딩의 설명용 이미지다. 조작 가능한 체험은 `/demo`의 기존 제품 컴포넌트에서 제공한다. `/demo`나 분석 방식 안내를 이미지로 교체하지 않는다. 갱신 방법과 기준 화면은 `src/assets/landing/README.md`, `e2e/landing-assets.spec.ts`에 둔다.
- 각 장면에 독립적인 스크롤 리빌을 적용하고 모션 감소 시 즉시 표시한다. 자동 재생·호버 전환·탭 선택은 제공하지 않는다. 설명 이미지의 대체 텍스트와 체험 링크의 키보드 접근을 유지한다.
- `서비스 소개`는 Hero, `주요 서비스`는 서비스 카탈로그로 부드럽게 스크롤한다. 사용자가 모션 감소를 요청한 환경에서는 즉시 이동해도 정보 구조와 기능이 동일해야 한다.

**3. 사용자 액션**

- 헤더·Hero·하단의 `로그인 없이 체험하기` 주 버튼 → 공개 [인터랙티브 데모](../screen-flow.md#2-인터랙티브-데모-wf-06)로 이동
- 공개 체험은 화면 맨 위에서 내용을 읽으며 내려가는 흐름을 유지한다. 안내 UI가 강조 버튼으로 화면을 자동 이동하거나 초기 포커스를 가져가지 않는다. 새 화면·재체험은 맨 위로 시작하고, 안내 내용 변경·화면 회전은 읽는 위치를 강제로 바꾸지 않는다.
- 회원가입·무료 시작 보조 버튼 → 랜딩 위에 [회원가입](#회원가입-ssignup) 라우트 모달 열기
- 서비스 소개·주요 서비스 → 해당 랜딩 영역으로 스크롤

## 회원가입 (SSignup)

**URL**: `/signup` — 랜딩 위의 회원가입 라우트 모달. 데스크톱 브랜드 패널·모바일 전체 화면·약관 딥링크와 자동 로그인은 유지한다.

브라우저 검증 화면: [데스크톱](../screens/email-signup-desktop.png) · [인증번호 입력](../screens/email-signup-code.png) · [인증 완료](../screens/email-signup-verified.png) · [320px 모바일](../screens/email-signup-mobile.png). Pencil 원본 반영 대상과 편집 상태는 [디자인 반영안](../../design/EMAIL_SIGNUP_GH181.md)을 따른다.

**인증 정책**

- 최초 진입마다 생성 SDK의 `GET /api/v1/auth/signup-policy`로 `verificationMethod`를 조회한다. `EMAIL`이면 이메일 인증만 표시하고 전화번호를 수집하지 않는다. `PHONE`이면 기존 이메일·비밀번호 가입 정보와 휴대폰 인증을 표시한다.
- Backend 기본 설정은 `EMAIL`이다. Front에 기본 인증 방식을 추측하는 fallback, 사용자 선택 토글 또는 별도 환경 변수를 두지 않는다.
- 정책 로딩·오류·알 수 없는 값에서는 발송과 가입을 막고 오류일 때 `인증 방식 다시 불러오기`를 제공한다. 서버 정책 변경 오류는 토큰을 폐기하고 정책을 재조회한다.

**입력·시간 정책**

| 항목 | 계약 |
| --- | --- |
| 이름(필명) | 필수, 최대 20자, 중복 허용 |
| 이메일 | 필수, 이메일 형식, 최대 255자, 중복 불가. 앞뒤 공백만 제거하고 대소문자를 보존한다. 인증·가입에 동일한 값을 보낸다. |
| 휴대폰 번호 | `PHONE` 정책에서만 필수, `010`으로 시작하는 11자리 숫자, 중복 불가 |
| 인증번호 | 6자리 숫자, 기본 유효시간 300초, 오입력 5회에서 해당 흐름 잠금 |
| 재전송 | 기본 대기 60초. 재전송 성공 시 최신 `verificationId`와 새 유효시간으로 교체 |
| 가입 토큰 | 인증 성공 후 기본 600초 동안 유효한 1회용 토큰. 가입 완료까지 남은 시간을 표시 |
| 비밀번호 | 8~64자, 영문·숫자 각각 한 개 이상 |
| 비밀번호 확인 | Front에서만 일치 검증 |
| 법률 확인 | 현재 게시 이용약관·개인정보처리방침을 한 체크로 동의·확인 |
| 나이 확인 | 별도 필수 체크로 만 14세 이상 확인, 생년월일은 수집하지 않음 |

인증 만료·재전송·가입 토큰 타이머는 모두 Backend 응답의 초를 사용한다. 화면에서 300/60/600을 상수로 재정의하지 않는다. 이메일 소유 인증은 실명·나이 확인을 대신하지 않는다.

**화면·상호작용**

1. 이름·이메일을 입력한다. `PHONE` 정책에만 휴대폰 입력이 추가된다.
2. 연락처 아래 전체 너비의 `인증번호 받기`를 누른다. 긴 이메일도 320px 화면에서 읽을 수 있으며 발송 중 중복 클릭은 차단한다.
3. 발송 성공 후 6자리 입력·`MM:SS` 만료 타이머·`인증` 버튼을 표시하고 재전송 대기 초를 버튼에 표시한다. 이메일 모드에서는 입력칸 아래 별도 안내 상자에 `인증메일이 도착하지 않았다면 스팸함도 확인해주세요.`를 표시하고 `스팸함`을 굵게 강조한다. 인증 완료 또는 이메일 변경 시 안내를 숨긴다.
4. 확인 성공 시 인증 완료 상태와 가입 완료까지 남은 시간을 표시한다. 인증번호는 화면 상태에서도 지운다.
5. 비밀번호·법률 문서·만 14세 이상 확인 후 가입한다. 가입·토큰 발급 한 요청 성공 시 자동 로그인하여 `/works`로 현재 히스토리를 대체한다.

- 인증 대상 이메일이나 번호를 바꾸면 토큰·인증번호·진행 상태를 즉시 폐기한다. 발송·확인 요청 중에도 연락처를 수정할 수 있다. 이전 주소의 늦은 성공·실패 응답은 새 흐름을 덮어쓰지 않는다. 이메일 대소문자 변경도 다른 주소로 취급하며 앞뒤 공백만 바뀌면 동일 주소다.
- 재전송 중 이전 인증번호 확인을 막는다. 인증번호 만료·오입력 한도에서 확인 입력을 닫되 남은 재전송 대기는 유지한다.
- 인증·법률·연령 확인 전에는 회원가입을 비활성화한다. 제출 중에는 인증 대상 입력·발송·확인을 잠근다.
- 로그인으로 전환할 때는 `/login`으로 대체한다. 랜딩에서 열었으면 닫기·뒤로가기로 복귀하고 직접 진입은 `/landing`으로 대체한다.

**저장소·세션**

| 저장 위치 | 저장 가능한 값 |
| --- | --- |
| `sessionStorage.catchhole_email_verification` | `verificationId`, `email`, `expiresAt`, `resendAt` |
| `sessionStorage.catchhole_phone_verification` | `verificationId`, `phoneNumber`, `expiresAt`, `resendAt` |
| 컴포넌트 메모리 | 인증번호·가입 토큰·비밀번호. 새로고침·모달 이탈 시 폐기 |

- 확인 성공·가입 성공 시 인증 진행 저장소를 지운다. 새로고침하면 성공 토큰을 복원하지 않으며 새 인증번호를 받아야 한다.
- 발송·확인·가입은 생성 SDK를 직접 호출하여 인증번호·비밀번호·가입 토큰이 공유 Query/Mutation 캐시에 남지 않도록 한다. 정책·법률 조회는 생성 TanStack Query 옵션을 사용한다.
- 모든 요청은 공통 `fetchWithAuth`와 `credentials: include`를 따른다. `signup-policy`, `email-verifications`, 기존 전화번호 인증·가입·로그인·refresh·logout에는 401 refresh 재시도를 적용하지 않는다.
- 가입 성공 시 access token은 localStorage에 저장하고 refresh token은 Backend의 HttpOnly 쿠키로만 다룬다. 실제 인증 저장 시 데모 데이터를 제거한다. 보호 화면에서는 `/auth/me`로 인증을 확인한다.

**API 계약**

| 요청 | 입력 | 성공 응답 `data` |
| --- | --- | --- |
| `GET /api/v1/auth/signup-policy` | 없음 | `verificationMethod: EMAIL \| PHONE` |
| `POST /api/v1/auth/email-verifications` | `email` | `verificationId`, `expiresInSeconds`, `resendAfterSeconds` |
| `POST /api/v1/auth/email-verifications/{verificationId}/confirm` | `code` | `emailVerificationToken`, `expiresInSeconds` |
| `POST /api/v1/auth/phone-verifications` | `phoneNumber` | 이메일 발송과 같은 형식 |
| `POST /api/v1/auth/phone-verifications/{verificationId}/confirm` | `code` | `phoneVerificationToken`, `expiresInSeconds` |
| `POST /api/v1/auth/signup` | `email`, `password`, `displayName`, 정책에 맞는 인증 토큰, 아래 법률 확인 필드 | `accessToken` 및 HttpOnly refresh 쿠키 |

회원가입에는 `termsAccepted=true`, `privacyPolicyAcknowledged=true`, `age14OrOlderConfirmed=true`, 사용자가 본 `termsDocumentId`, `privacyPolicyDocumentId`를 보낸다. Backend가 같은 트랜잭션에서 현재 게시본을 검증하고 문서 FK·종류·버전·행위와 서버 기록 시각을 보존한다. 전화번호는 가입 body에 직접 보내지 않고 인증 토큰에 연결된 값을 사용한다. 이메일 인증은 토큰의 주소와 가입 이메일이 일치해야 한다.

`MemberResponse`는 `emailVerified`와 기존 `phoneVerified`를 독립 제공한다. 이메일 가입자는 `phoneNumber=null`, `phoneVerified=false`, `emailVerified=true`이다. 기존 회원의 이메일 인증을 완료한 것으로 추측하지 않는다.

## 계정 최초 분석 안내

- 회차 업로드의 반영 방식 안내는 현재 작품이 아닌 **계정 전체 첫 분석 전** 한 번만 자동으로 표시한다. 생성 SDK의 `GET /api/v1/analysis-mode-guides`, `POST /api/v1/analysis-mode-guides/claim`을 사용한다. `auth/me`의 회원 ID로 Query 캐시를 구분하며 타 계정 상태를 공유하지 않는다.
- 서버의 `shouldShow`만 사용하며 localStorage·작품별 성공 수·프론트 목록 합산으로 자격을 추측하지 않는다. 서버 조회·선점 실패는 업로드를 막지 않고, 수동 도움말은 계속 제공한다.
- 안내는 실제 업로드·검토·프로필 컴포넌트에 가상의 데이터를 넣어 한 줄 5단계로 전체 3개 직접 검토, 명확한 2개 자동 저장, 모호한 1개 직접 검토를 설명한다. PNG·방식 탭은 없고 예시 안은 inert로 조작을 차단한다. 사용자 입력·확정 실습은 없다. 실제 분석·원고·설정 변경은 요청하지 않고 업로드 입력/반영 방식도 바꾸지 않는다. 계정의 안내 기록만 서버에 남는다.
- UI·URL·키보드·모바일 동작은 [첫 분석 안내](../analysis-mode-guide.md)를 따른다. Pencil `gh194AnalysisGuideDesktop`/`gh194AnalysisGuideMobile`과 실제 API 화면을 함께 관리한다.

- 2026-10-12 `/demo` 세계관 안내는 URL의 `settingId`로 현재 상세 열림을 구분한다. 다른 세계관 상세에서는 닫기 버튼을, 닫힌 목록에서는 거꾸로숲 카드를 강조한다. 가려진 배경 카드의 테두리가 상세창 위에 겹치지 않으며 API·인증·저장소 계약은 그대로다.

- 2026-10-12 `/demo` 결과 탐색에서는 특정 원문 근거 열람과 무관하게 `체험 마치기`를 제공한다. 결과 탐색의 수정값은 메모리 입력값이며 API·브라우저 저장소에 저장하지 않는다. 회원가입 라우트와 재체험 초기화 계약은 유지한다.

- 2026-10-12 최종 교정: `/demo`는 세계관 원문 확인 이력을 현재 펼침 상태와 별도 메모리로 유지한다. 확인을 마친 뒤 자유 탐색 중에도 완료 안내를 유지하고 안내 강조를 종료한다. 완료 화면은 사용자 버튼으로만 진입한다. 재체험·새로고침으로 이력 초기화, API·저장소 사용 없음. 완료 디자인은 아래 최종 이미지 시안으로 대체한다.

- 2026-10-12 최종 이미지 시안: 완료 화면은 생성한 종이책 세계관 이미지와 실제 텍스트·회원가입/재체험 버튼으로 구성한다. 사용자 요청으로 하단 체험 기록을 제거했다. 가상 데이터 고지·메모리 기반 체험·기존 인증 이동 계약은 유지한다.


### GH241 챗봇 질문 입력 상태 보완 (2026-10-14)

질문 접수 성공 후 출처 회차 입력을 비워 다음 질문으로 자동 계승하지 않는다. 접수 응답 유실 시 같은 요청의 범위·멱등 키는 보존한다. 답변이 도착했어도 `SETTLEMENT_PENDING`이면 정산 완료까지 새 질문과 재시도를 잠그고 2초 상태 조회를 유지한다. 공통 계약은 [일회성 대화 문서](../chat-sessions-v1.md)를 따른다. 기능 활성화·운영 배포를 의미하지 않는다.

답변 제한은 정확히 같은 문장만 합친다. 안내가 하나면 바로 표시하며, 여러 개면 `답변에서 확인할 점 N가지`의 펼치기/접기로 모든 서버 문장을 확인한다. 문장·고유명사·설정값을 분류하거나 치환하지 않고 접힌 목록에도 원문을 보존한다. 버튼은 펼침 상태와 상세 영역을 연결하며 키보드 조작과 44px 터치 높이를 제공한다. 직접 근거 일부의 조회 실패는 실패 건수로 알리고 다른 직접 근거와 검색 인용은 유지한다. 마지막 질문 재검증 실패·실행 변경은 모든 인용 표시를 막으며 인증·세션 캐시 경계는 유지한다.

근거 창은 `sources`와 `retrievalSources`의 배열 순서를 이은 `근거 N`을 사용하며, 조회 실패 항목 뒤의 번호도 재배치하지 않는다.


2026-10-15 대화방 목록·스크롤 보완은 기존 생성 시각·질문 수와 인증된 API만 사용한다. 추가 API·본문 저장·인증 계약 변경은 없으며 2시간 만료와 인증 세대·작품·세션별 캐시 경계를 유지한다. 질문 접수 뒤 조회 복구에 사용할 질문 ID도 현재 대화의 메모리에만 보관하며 페이지·방 이동 시 자동 이동을 취소한다. 접수 후 목록 재검증과 확인된 질문 수의 캐시 동기화도 같은 인증 세대·작품 경계를 사용하며 API·저장 계약을 추가하지 않는다. 화면의 고정 제외 안내 중 `관련 설정이 없는 N명/개` 집계만 생략하고 미검토·판단 보류 의미는 보존한다. 상세 동작은 [대화방 탐색과 읽기 위치](../chat-sessions-v1.md#대화방-탐색과-읽기-위치-2026-10-15)를 따른다.
