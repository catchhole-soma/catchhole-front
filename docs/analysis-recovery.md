# GH201 분석 실패와 복구 안내

분석은 회차별 Job으로 실행·재개하고, 모든 현재 회차가 완료되면 기존 `batchId` 검토 화면을 연다. 앞 회차 실패로 뒤 회차가 대기하더라도 완료된 일부 후보의 검토·확정을 먼저 열지 않는다. 잔여 분석 취소·포기, 부분 완료, 새로운 회차별 검토 API는 이번 범위가 아니다.

## 생성 거절

| 서버 오류 | 화면의 다음 행동 |
| --- | --- |
| `ANALYSIS_FUTURE_HISTORY_CONFLICT` | 같은 batch의 자동 생성 재시도를 제거한다. 원고 저장 성공을 알리고 원고 목록의 기존 회차별 재분석·직접 검토 경로로 안내한다. |
| `ANALYSIS_ORDERED_JOB_RETRY_REQUIRED` | 새 분석 생성 대신 기존 분석 목록에서 중단된 회차의 재개 여부를 확인하도록 안내한다. |
| 일반 `ANALYSIS_RUN_MODE_INVALID`, 일시적 작업 충돌·네트워크 오류 | 명시적 영구 거절로 추측하지 않는다. 서버 오류를 표시하며 정상 재시도를 유지한다. |
| `AI_TOKEN_QUOTA_EXHAUSTED` | 기존 공통 사용량 안내를 유지한다. 재시작 확인창이 열려 있었다면 닫는다. |

새 원고 저장 후 생성이 거절되어도 재업로드를 요구하지 않는다. 과거 다회차 업로드도 기존 원고 목록의 개별 `MANUAL` 분석을 활용하며, 자동으로 모드를 바꾸거나 유료 분석을 시작하지 않는다. 무효화된 기존 분석의 확인창도 명시적 거절 이후 실행 버튼을 해당 목록 이동으로 바꾼다.

사전 eligibility API는 추가하지 않는다. 서버가 생성 시점에 최종 판단하고, 프론트는 명시적인 오류 code로 현재 화면의 반복 요청을 막는다. 이 화면 상태를 확정 이력이나 서버 실행 가능 여부의 영구 캐시로 사용하지 않는다.

## 실패한 회차 재개

예: 1~2화 완료 → 3화 실패 → 4~5화 대기 → 3화부터 재개 → 전체 완료 후 batch 검토.

재개 응답이 유실되거나 동시 요청으로 409를 받아도 서버에서는 같은 Job이 이미 재개됐을 수 있다. 요청했던 기존 Job을 즉시 다시 조회하고 실행 중·완료 상태가 확인되면 이전 재개 오류를 계속 표시하지 않는다. 교체된 과거 Job 전체를 다시 polling하거나 새 run을 만드는 방식으로 복구하지 않는다.

`ANALYSIS_JOB_SUPERSEDED`는 더 최근의 분석이 있어 과거 Job을 재개할 수 없다는 명시적 거절이다. 해당 Job의 재개 버튼을 최신 분석 목록 이동으로 바꾼다. 일반 409만으로 이 상태를 추측하지 않는다.

## 후보 상세

캐릭터·세계관 ordered 후보는 서버의 개별 비교 재시도 API 대상이 아니다. `manualReviewAvailable`인 자동 완료 후보는 기존 직접 검토를 유지한다. 그 외 실패·재비교 필요 후보에는 개별 재비교 버튼을 숨기고 분석 목록에서 회차의 재개 여부를 확인하도록 설명한다. 세계관 후보의 자동 재비교 effect도 ordered 후보를 제외한다.

## 원고 교체와 해당 회차 재분석

파일 교체는 해당 회차의 원문·미확정 후보만 교체하고, 이미 완료된 뒤 회차의 분석 결과는 보존한다. 파일 변경 자체로 LLM 분석을 시작하지 않는다. 사용자가 원고 목록의 재분석 확인창에서 시작해야 해당 `episodeId`의 `SETTING_EXTRACTION + MANUAL`을 요청한다. 기존 기본 `CONFIRMED_ONLY` 모드를 유지한다.

직접 검토에서 확정하면 기존 공통 반영 정책으로 현재값 적용 여부를 판단한다. 뒤 회차의 같은 항목이나 직접 수정한 값이 있으면 현재 설정을 유지하고 해당 회차의 이력에 저장하며, 그 외에는 선택한 반영 방식에 따라 현재 설정도 바뀔 수 있다. 캐릭터·세계관의 `historyOnly` 표시에는 분석 모드 제한을 두지 않는다. 이력 저장 여부를 제안 operation이나 회차 번호만으로 추측하지 않는다.

이미 입력을 고정한 미완료 분석과의 충돌은 서버의 제한을 표시한다. 과거 무효화된 후속 작업을 프론트에서 정상 완료로 추정하거나, 완료된 후속 회차를 자동 재분석하지 않는다.

## 회귀 확인

- `e2e/ordered-analysis.spec.ts`: 기존 순차 재개·전체 완료, 생성 거절 구분, 응답 유실/충돌 후 같은 Job 상태 복원.
- `e2e/upload-policy.spec.ts`: 과거 단일·다회차 원고 보존, 같은 자동 생성 반복 차단, 기존 원고/분석 목록 안내.
- `e2e/automatic-review.spec.ts`: 기존 직접 검토 보존, legacy ordered 개별 재비교 요청 차단.
- `e2e/manuscript-analysis-refresh.spec.ts`: 파일 교체 후 해당 회차만 명시적으로 직접 검토 재분석, 완료된 후속 회차 표시 유지.
- `e2e/setting-review.spec.ts`, `e2e/world-setting.spec.ts`: `CONFIRMED_ONLY` 확정 결과의 이력 저장 표시.

목 API 브라우저 테스트는 UI 계약 검증이며 운영 원고, 실제 LLM 분석, 서버 트랜잭션의 동작을 대신 검증하지 않는다.

### 2026-09-22 실행 결과

- 관련 Playwright 146개 통과: ordered-analysis, upload-policy, automatic-review, analysis-list, manuscript-analysis-refresh, setting-review, world-setting의 143개와 원고 재분석 smoke 3개. 원고 교체 후 자동 분석 요청이 없고 명시적으로 해당 회차만 MANUAL 생성하는지, 320px 재분석 모달 버튼 접근, 양쪽 `CONFIRMED_ONLY` 후보의 `historyOnly` true/false를 포함한다.
- 실제 백엔드 테스트 서버의 OpenAPI로 SDK 재생성 후 typecheck·build 통과. lint 오류 0(기존 React Refresh 경고 2), check:unused 통과. React Doctor는 전체 기존 진단 173개를 보고했으며 깨끗한 결과로 간주하지 않는다.
- 임시 Vite(3103) → 실제 Spring Boot/H2(8083)에서 JWT 인증된 테스트 계정으로 확인했다. 과거 확정 이력의 자동 생성 거절은 HTTP 400 + `ANALYSIS_FUTURE_HISTORY_CONFLICT`이며 같은 실행 버튼이 사라지고 원고 목록으로 안내한다. 작업 수는 2개 그대로여서 거절된 요청이 새 분석을 만들지 않는다.
- 기존 INVALIDATED 1화의 원고 목록 상태와 재분석 버튼을 확인했고, 명시적인 직접 검토 요청은 HTTP 200으로 해당 회차 MANUAL Job 1개를 생성했다. 기존 이력은 보존된다. Worker/LLM은 실행하지 않았다.
- 검증 서버·DB는 별도로 격리했다. 운영 데이터, 실제 PostgreSQL 부하, 실제 AI 응답 품질은 이 검증 범위가 아니다.
