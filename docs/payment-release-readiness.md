## 심사용 일반 계정 생성·전달 절차

현재 계정은 **없으며 절차만 준비**했다. 관리자 계정이나 기존 개인 작품 계정을 제공하지 않는다. 신규 일반 계정은 자신의 비어 있는 작품 공간만 보며, 별도 심사자 역할을 추가하지 않는다.

1. 운영팀이 수신·관리할 수 있는 새 이메일을 정한다. 기존 회원과 중복되지 않는지 가입 화면에서 확인한다. 이름(필명)은 `캐치홀 심사`처럼 용도를 식별할 수 있게 정할 수 있다.
2. 실제 서비스의 회원가입 화면을 연다. 가입 화면이 조회한 `signup-policy`에 따라 이메일 또는 휴대전화 인증을 한다. 인증 방식은 임의로 우회하거나 고정하지 않는다. 휴대전화 방식이면 기존 회원과 중복되지 않는, 사용 권한이 있는 번호가 필요하다.
3. 담당자가 인증번호와 전용 비밀번호를 직접 입력한다. 현재 비밀번호 조건은 8~64자, 영문·숫자 각각 1개 이상이다. 다른 계정에서 쓰는 비밀번호를 재사용하지 않는다. 약관·개인정보처리방침과 만 14세 이상 확인 후 가입한다.
4. 로그아웃한 새 브라우저 세션에서 이메일·비밀번호로 다시 로그인한다. 일반 회원이고 개인 원고·결제 내역이 없음을 확인한다. 화면 검수에 작품이 필요하면 팀이 권리를 가진 공개용 샘플만 준비한다.
5. 생성된 계정의 회원 번호를 서버 `PAYMENT_REVIEW_MEMBER_IDS`에 등록하고 기능을 활성화한다(운영 설정 변경은 별도 승인 후). 배포 후 `https://www.catchhole.com/billing`의 상품·약관·사업자 표시와 카드 결제창 진입을 확인한다. 새 계정을 만들었다는 것만으로 `/billing`이 공개되는 것은 아니다. 아래 배포 조건이 충족되어야 한다.
6. 이니시스의 로그인 정보 제출란 또는 지정된 안전한 제출 경로에 URL·계정·비밀번호를 전달한다. GitHub 이슈, 저장소, 로그, 화면 캡처에는 비밀번호를 남기지 않는다. 심사자는 가입이나 인증번호 수신을 다시 하지 않고 기존 계정으로 로그인할 수 있어야 한다.
7. 보완 심사까지 끝난 뒤 전용 비밀번호를 변경하거나 계정을 회수한다. 담당자·생성 여부·제출 여부·회수 여부만 내부 기록에 남긴다.

## 개정 약관 준비와 게시

준비 원문:

개정안은 로컬 미리보기와 허용된 심사 계정의 `/billing/terms`, `/billing/privacy`에서 검토한다. 서버의 보호된 `payment-reviews/page`가 원문을 반환하며 일반 회원은 조회하지 못한다. 기존 `2026-08-24` 게시 원문과 동의 기록은 수정하지 않았다. 결제·거래 기록 보관, 포트원·이니시스 처리, 잔여분 환불과 탈퇴 시 거래 증명 자료의 분리 보관을 개정안에 넣었다. 개인정보처리방침의 공개 내용은 판매 구현 및 실제 위탁 계약과 일치하는지 출시 전에 대조한다.

게시 순서:

1. 고객센터·통신판매업 처리를 끝내고 문구를 채운다. 결제 정보의 실제 수집·저장·위탁 항목, 구매자 정보의 외부 전송과 보유·파기 주기를 구현/계약에 맞춰 대조한다.
2. 공고일·시행일·문서 버전을 정한다. 기존 약관의 일반 변경 7일, 중요·불리한 변경 30일 사전 고지 기준과 별도 동의 필요 여부를 검토한다. 오늘 날짜를 임의 시행일로 쓰지 않는다.
3. 새 문서의 확정 원문을 UTF-8·LF로 고정하고 SHA-256을 산출한다. 현재 Backend 법률 타입은 `TERMS_OF_SERVICE`, `PRIVACY_POLICY` 두 종류다. 구매조건을 임의의 새 enum으로 넣지 않는다.
4. 운영 변경이 승인된 후 두 개정 원문을 새 `DRAFT` 행으로 준비한다. `effective_date`, `published_at`, `retired_at`은 DRAFT일 때 null이어야 한다. 실제 DB ID를 발급받고 원문·해시를 확인한다. 이번 작업에서는 DB 행을 생성하지 않았다.
5. 시행 시점에 기존 `PUBLISHED`를 `RETIRED`로 바꾸고 새 문서를 `PUBLISHED`로 전환하는 작업을 하나의 트랜잭션에서 수행한다. 종류·locale별 게시본 하나 제약을 지키고 `published_at`, `effective_date`, `retired_at`과 과거 기록을 보존한다.
6. **현재 API는 `status=PUBLISHED`로 현재 문서를 선택하며 미래 시행일을 필터링하지 않는다.** 미래 날짜를 넣어 미리 PUBLISHED로 만들면 곧바로 새 가입 동의 대상이 된다. 공지는 별도로 하고 실제 전환 시점을 관리한다.
7. `/terms`, `/privacy`, 가입 모달에서 같은 ID·버전·해시·원문을 확인한다. 가입 도중 문서 교체 시 재확인되는지 검증한다. 기존 회원의 유료 구매 동의·구매조건 스냅샷 기록은 실제 결제 백엔드 작업에서 연결한다.

개정안의 기간 만료 자동 환불, 시스템 오류 차감 복원, 탈퇴 후 거래 기록 분리 보관은 아직 구현된 기능이 아니다. 실판매 전 기능 검증이 필요하다. 기존 무료 이용·탈퇴 동작을 유료 판매 준비 완료로 간주하지 않는다.

## 배포 직전 실행 순서

1. 변경 diff와 이 문서의 미완료 항목을 리뷰한다. 원본 프론트와 다른 작업 중인 백엔드를 건드리지 않는다. 프론트·백엔드의 `feat/gh-441-payment-review` PR을 함께 리뷰한다. PR 생성은 11월 19일 사용자 요청 범위이며 운영 배포·머지는 포함하지 않는다.
2. 이번 준비에서 최신 `origin/main`의 `84b5d15`까지 fast-forward하고 문서·앱 import 충돌을 해결했다. 배포할 때 main이 다시 바뀌었다면 추가 변경을 확인한다. 프론트 push/PR은 Vercel 미리보기를 시작할 수 있다. 운영 기본 OFF와 서버의 빈 허용 목록을 유지한다.
3. 백엔드를 먼저 배포한다. 기본값은 `PAYMENT_REVIEW_ENABLED=false`, `PAYMENT_REVIEW_MEMBER_IDS` 빈 목록이다. 심사용 회원 번호와 확인된 TEST 채널을 등록하고 서버 기능을 켠 뒤 프론트를 `VITE_PAYMENT_REVIEW_ENABLED=true`로 빌드한다. 어느 쪽이 꺼져 있거나 목록이 비었으면 일반 회원에게 충전을 열지 않는다. 프론트를 먼저 배포해도 서버 API 미존재/실패는 접근 거부다.
4. 공개 환경에서 사용할 PortOne 채널이 콘솔의 **TEST / KG이니시스 / inicis_v2 / INIpayTest**인지 다시 확인한다. 변수 이름의 TEST나 `channel-key-` 접두사만으로 실채널을 배제할 수 없다. 서버 결제 검증·지급이 없는 현재 구현에 실채널을 연결하지 않는다.
5. 프론트 환경변수: `VITE_PAYMENT_REVIEW_ENABLED`, `VITE_CUSTOMER_SERVICE_PHONE`, `VITE_MAIL_ORDER_REGISTRATION`. `VITE_PORTONE_TEST_*`는 개발 전용이며 운영에서는 사용하지 않는다. 서버 환경변수: `PAYMENT_REVIEW_ENABLED`, `PAYMENT_REVIEW_MEMBER_IDS`, `PAYMENT_REVIEW_STORE_ID`, `PAYMENT_REVIEW_CHANNEL_KEY`. `VITE_*`는 공개 값이다. API secret·signkey·INIAPI Key·계정 비밀번호는 넣지 않는다.
6. 법률 문서 게시/공지 일정과 사이트 반영 순서를 맞춘다. 로컬 개발 경로를 운영 상품 URL로 제출하지 않는다. 승인된 배포 뒤 실제 도메인에서 일반 계정의 메뉴 숨김·직접 주소 차단 및 심사 계정의 상품·금액·지급량·약관 일치, 사업자 하단, 카드 창 표시·취소 복귀와 모바일을 확인한다.
7. 이니시스 신청서의 상품·12개월 제공기간·환불·사이트 주소·심사용 계정 정보를 대조한 뒤 심사를 요청한다. 계약서의 등록비·연관리비·정산 조건·보증보험 요구액/보험료가 앞서 합의한 조건과 달라지면 알린다. 이 작업만으로 비용 면제나 심사 승인을 확정하지 않는다.

문제가 있으면 서버 허용 목록을 비우거나 서버 플래그를 OFF로 적용해 다음 자료 조회·결제창 요청을 차단하고, 프론트 플래그를 OFF로 빌드하여 메뉴·`/billing`을 닫는다(Vite 변수는 빌드 시점에 반영됨). 게시된 약관의 원문을 제자리에서 수정하거나 과거 동의 FK를 삭제하지 않는다.
